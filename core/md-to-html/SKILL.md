# MD to HTML

Use this skill when a user wants a Markdown document rendered into a readable local HTML file.

This skill is intentionally **on-demand**. Do not render an entire documentation tree unless the user explicitly asks for a batch conversion.

## When To Use

Use this skill when:

- the user asks to convert a specific `.md` file to HTML for easier reading
- the user wants a small set of named Markdown files rendered locally
- a document contains embedded HTML/SVG and the user wants a browser-friendly version

Do not use this skill when:

- the user has not asked for HTML output
- the user only wants the Markdown edited
- the user has not identified which files should be rendered

## Default Behavior

1. Confirm the exact Markdown file or files to render.
2. **Preflight Check**: Verify all diagram blocks in the source against `md-diagram` rules (see § Preflight below). Fix any syntax flaws in the source Markdown before rendering.
3. Render only those explicit targets using the bundled `render.py`.
4. Write output to `docs/html/` unless the task clearly requires another location.
5. When fewer than three documents are rendered, generate only their HTML files and do not generate `index.html`; generate the index only for batch runs of three or more.
6. Preserve embedded HTML/SVG content.
7. Report the generated HTML file paths back to the user.

## Command

This skill is **self-contained** — it ships with its own renderer (`render.py` in the same directory as this `SKILL.md`). No project-level render script is needed; invoke the skill's bundled engine directly.

The skill's renderer provides:

- **Mermaid chart support out of the box**: the HTML template already injects the `.mermaid` container CSS and `mermaid.initialize` parameters from `md-diagram` (§4). Mermaid fenced blocks are automatically rendered in `<pre class="mermaid">` with raw unescaped syntax so Mermaid 11.x renders them reliably.
- **List aggregation**: ordered and unordered lists are rendered with `sane_lists` and multi-line continuation, preventing all items from resetting to `1.`
- **Fixed light theme at 1280px+**: wide layout, no dark-mode clashing with hand-drawn SVG

```bash
python <path-to-skill>/render.py <path-to-file.md> [<path-to-second-file.md> ...]
```

Example (from the project root, using the active Python environment):

```bash
python "$HOME/<skills-dir>/md-to-html/render.py" docs/design-notes.md
```

The renderer requires Python 3.9+ and the `Markdown` library. If the project does not have it installed, run:

```bash
python -m pip install Markdown
```

This is a one-time setup per project; the skill itself carries no other dependencies.

## Guardrails

- Never omit the input paths.
- Never default to the whole `docs/` tree.
- If the user wants only one file, render only one file.
- When fewer than three files are rendered, do not generate `index.html` (and remove any stale one left by an earlier run).
- If stale HTML generated by earlier blanket runs is obviously no longer needed, clean it up carefully and mention what was removed.

## Preflight Check Against `md-diagram` Rules

Before invoking `render.py`, the agent **MUST** inspect every ` ```mermaid ` block in the target Markdown file against the `md-diagram` checklist (see `md-diagram` §6):

1. **[CHK-2] Edge endpoint compliance**: all arrow endpoints (`-->`, `-.->`, `==>`) must connect to concrete entity nodes (Node IDs); never point edges at a nested subgraph's frame ID (`subgraph ID`), otherwise Mermaid 11.16+ throws `Syntax error in text`.
2. **[CHK-3] Edge symbol rules**: are thick arrows strictly the standard `==>` or `==>|label|`, never with extra equals signs (e.g. `====>`)?
3. **[CHK-4] Edge label cleanliness**: do `|...|` labels avoid unescaped bare parentheses `()` and path slashes `/`; use plain words and spaces?
4. **[CHK-8] Entity symbol conflicts**: is a bare `&` absent from node/label text (use `and` or `#38;` instead) to avoid XML/HTML parser conflicts?
5. **[CHK-1] Subgraph title concise**: do all subgraph titles stay short single lines ($\le 10$ CJK chars) with no long parenthetical explanations, avoiding occlusion of inner nodes?

If any violation is detected in the Markdown source, **fix the Markdown source first**, then run `render.py`.

## Renderer Contract

Rendering is provided by this skill's bundled script `render.py` (in the same directory as this `SKILL.md`). The decisions below are baked into that renderer and are the parts worth keeping:

1. **On-demand single-file rendering**: accept explicit input paths only — never scan the whole `docs/` tree by default. Generate `index.html` only when three or more documents are rendered; for fewer than three, output only the requested HTML files.
2. **Output layout**: write rendered files under `docs/html/`, mirroring the source's relative path.
3. **Fixed light theme**: the HTML template pins `color-scheme: light` and must NOT follow the OS dark mode via `@media (prefers-color-scheme: dark)`. Rationale: hand-written structural SVG is designed on a white canvas (see `md-diagram` §3.1 dark-mode isolation); flipping the page to dark produces clashing page/chart contrast and invisible headings.
4. **Wide layout**: `--max-width` on the content container should be at least `1280px` (never below the diagram viewBox width such as `1120`), so large SVG diagrams are not squashed into a narrow column. Diagrams render with `width="100%" height="auto"`.
5. **Markdown extensions**: render with `extra` (tables / fenced code / attr_list), `toc`, `sane_lists`, and `nl2br`, output format `html5`.
6. **Title extraction**: derive the `<title>` from the first `# ` level-1 heading in the source.

## Output Expectations

After rendering, provide:

- which Markdown files were rendered
- which HTML files were generated
- any caveats about embedded HTML/SVG portability across platforms
